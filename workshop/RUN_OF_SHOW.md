# Three-hour workshop run of show
This timing assumes prework is complete and the runtime + chosen Solana starter have passed host and fresh-user rehearsal. Otherwise use the explicitly labeled off-chain rehearsal and do not advertise a deployed on-chain result.

| Minute | Activity | Output |
|---|---|---|
| 0–10 | Show one useful app and the evidence that it works | Shared goal, not a token-price lecture |
| 10–20 | User problem, market question, exact resolution and template | Completed brief |
| 20–30 | Three discovery agents; humans challenge user need | Evidence/product/architecture notes |
| 30–40 | Read the decision memo; founder approves a narrow scope | Frozen brief and approved build |
| 40–110 | Parallel app/domain/submission work; mentors unblock | One differentiated primary flow |
| 110–130 | Feature freeze; integration and browser/chain checks | Recorded pass/fail evidence |
| 130–150 | Pitch and technical-demo preparation | Local submission draft + continuation |
| 150–175 | Demos; 2 min/team with a capped queue | Product and evidence shown |
| 175–180 | Feedback and next deadline | Next action and ownership |

25 minutes supports roughly ten teams at two minutes plus transitions. Larger cohorts require parallel demo rooms or a shortlist; never promise every team a stage slot that the agenda cannot contain.

## Host assignments
Assign a product/workshop facilitator and an ecosystem/event coordinator. Name a separate chain engineer if neither owns protocol implementation. Confirm these assignments before the session.

## Milestones
By minute 40: one approved scope. By minute 80: primary flow visible. At minute 110: no new features. At minute 130: a demonstrable result or an honest broken-state explanation. Cut extra integrations, secondary screens and analytics before cutting verification.

## Failure policy
Provider failure: capture it; use the explicit rehearsal template for learning, with fixture labels intact. Solana/RPC failure: keep the useful offline flow, explain what is not connected and record the blocker. Never relabel a simulation as a live fallback. No participant should need to reveal a key or fund a mainnet wallet for the event.

## Host toolkit submission versus local judging
PredictKit is the host product being evaluated by use, not an entry that the hosts award their own local prize. Participants submit distinct projects. Disclose the shared base and mentor role. Obtain permission before publishing demo footage, usage measurements or participant repos.
