# PredictKit
## Decision
Build an open-source, evidence-first studio for creating prediction applications on Solana with a visible parallel agent team. Keep the domain toolkit and orchestration experience inside one product. Do not start a separate generic company-management platform.

**Working positioning:** From a clear prediction-app brief to a working product and an evidence-backed launch pack.

## Initial user and job
The first user is a capable generalist developer or technical founder in a Solana build sprint, supported by an event organizer. They need a differentiated app rather than a blank repository, and need to understand and prove what their agents built. The first distribution experiment is a small builder workshop. Organizational affiliation, sponsorship and official endorsement are not assumed.

The hypothesized problem: builders spend scarce event time on setup, incompatible APIs, unclear resolution rules, agent coordination and last-minute presentation. Validate this with observed sessions. Do not treat this paragraph as established customer research.

## The product's three parts
1. Domain foundations: market metadata, forecast/outcome semantics, resolution policies, provider boundaries, tests and reusable templates.
2. Builder Studio: a short brief, role graph, approval gate, real state, artifacts and continuation tasks.
3. Evidence Pack: code provenance, checks, chain proofs when available, pitch, technical demo and submission checklist.

Our differentiation hypothesis is the combination, not the invention of agent orchestration or prediction markets. Generic agent managers, coding agents and market SDKs already exist; see docs/SOURCES.md. PredictKit must prove domain-specific reliability and time-to-working-app.

## MVP contract
A new builder can understand a sample brief, choose a starter, run a bounded team, approve scope, inspect a generated app, see the exact implementation state and export a draft pack. To claim the full Solana MVP, at least one supported starter must also perform a meaningful verified Solana-backed operation. A decorative wallet connection or memo-only transaction is insufficient.

## Three templates, staged honestly
Forecast Studio is the first complete reference flow: make a forecast, close, record YES/NO/VOID, inspect calibration. Market Explorer and Resolution Desk share its browser code but start on different surfaces. All three shipped examples are OFF-CHAIN SIMULATIONS. A live market-data adapter and a devnet registry are future implementation tickets, not hidden features.

## Not in the first release
A new AMM, order book, token launch, mainnet custody, autonomous trading, generic agent marketplace, twenty always-on workers, full CRM, billing stack, or simultaneous Paperclip/Hermes/Codex/Agents SDK integrations. No real-money activity at the workshop.

## Proposed ownership, subject to agreement
A product owner handles scope, onboarding and participant experience. An event coordinator handles workshop logistics. A designated Solana engineer owns protocol integration and transaction tests. Confirm assignments before a pilot. Humans approve public attribution, licensing and submission decisions.

## Validation targets, not achieved metrics
First, three fresh builders complete the reference path without rescue. Then run the workshop with a recorded denominator: attempts, completions, time, assistance, costs and failures. Aim initially for at least 70% completing the agreed flow; change this target after the rehearsal rather than presenting it as a result. Compare against an equivalent starter without the agent workflow before claiming speed gains.

## Business hypothesis
Free open-source core; optional hosted team workspaces, cohort operations and supported integrations later. The likely first buyer is an ecosystem developer-relations or education organizer; this is not yet validated. Do not add a transaction fee, token or marketplace just to make the business sound larger. Continued use and willingness to pay must justify further expansion.

## Stop / continue criteria
Continue after a real multi-agent run, one meaningful chain-integrated flow and three independent builder tests. Narrow or pause if most time goes into runtime setup, if the chain is ornamental, or if teams cannot explain their own generated code. The workshop is useful even when results expose problems, but do not call that product-market fit.
